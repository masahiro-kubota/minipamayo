# MiniPamayo 懸念点・リスク分析

設計書 v0.3 / 実装計画に基づき、実装時に躓きやすいポイントを整理する。

---

## 躓きリスクの優先順位

| 順位 | 懸念 | Phase | 影響範囲 |
|---|---|---|---|
| **1** | VLM 構築（Adapter が機能するか） | 2a | 全 Stage に波及 |
| **2** | ドメイン SFT データ品質 | 2b | Stage 3-4 の性能上限 |
| **3** | Flow Matching の正しい実装 | 6 | Stage 2 の成否 |
| **4** | GT 制御列の逆算精度 | 4 | Stage 0 以降の学習ターゲット品質 |
| **5** | 離散トークン量子化設計 | 5 | Stage 1, 3, 4 の精度 |
| **6** | RL の不安定性 | 8 | 最終性能（ただしスキップ可） |

**最大のリスクは Phase 2（VLM 構築）**。ここを早期に通過できるかがプロジェクト全体の成否を左右する。

---

## 1. VLM 構築が最大のボトルネック

**Phase 2a ／ 深刻度: 高**

DINOv2 + Qwen2.5-0.5B を「VLM として機能させる」のは自明ではない。

- **Adapter の設計が鍵**: DINOv2 の出力（256×768）を Qwen2.5-0.5B が「視覚情報」として理解できる形に変換する必要がある。平均 Pool + Linear で本当に情報が伝わるかは不明
- **Feature Alignment のデータ量**: LLaVA は 558K の画像-キャプションペアで Alignment を行った。0.5B の小さい LLM で同等の効果を得るのにどの程度必要かは実験次第
- **VLM が動かないと全部止まる**: 後段の全 Stage がこの VLM の品質に依存する。ここで数週間ハマる可能性がある

### 対策

- Adapter は最初は平均 Pool + Linear で fail-fast
- 画像を入れて簡単なキャプションが出るかをまず確認
- Phase 2 と Phase 3 を並行で進める手もある（VLM 完成前に、ランダム初期化 LLM + DINOv2 で Stage 0 のパイプラインだけ先に通す）

---

## 2. ドメイン SFT のデータ品質

**Phase 2b ／ 深刻度: 高**

- **auto-labeling の品質上限がそのまま性能上限**: 教師 VLM（GPT-4o 等）に運転シーンの QA を生成させるが、プロンプト設計で品質が大きく変わる
- **API コスト**: 数万フレーム分の auto-labeling は GPT-4o だと高額。プロンプト試行錯誤のイテレーション回数が制約される
- **公開データセットの制約**: nuScenes は約 40K フレーム、comma2k19 はフロントカメラのみ。データの多様性が低い

### 対策

- まず小規模（数千フレーム）で回して品質を目視確認してからスケール
- 安価な API（Claude Haiku 等）でラフに回し、高品質版は少量に絞る

---

## 3. 制御ベース表現の GT 逆算

**Phase 4 ／ 深刻度: 中**

- **ego pose → (a, κ) の逆算精度**: GPS/IMU ベースの ego pose にはノイズがある。Tikhonov 正則化で平滑化するが、急旋回や急ブレーキで精度が落ちる可能性
- **数値的安定性**: Euler 積分の累積誤差。6.4 秒 64 ステップの積分で軌道が発散しないか
- **データセット依存**: nuScenes は 2Hz アノテーション（ego pose は補間で 10Hz に上げる必要がある）

### 対策

- 逆算した (a, κ) を再積分して元の軌道と比較する**往復テスト**を必ず実装
- 乖離が大きければ正則化パラメータを調整

---

## 4. 離散トークンの量子化設計

**Phase 5 ／ 深刻度: 中**

- **ビン数と範囲の選定**: 加速度 a と曲率 κ の値域がデータセットに依存。範囲を狭くすると外れ値がクリップされ、広くすると分解能が落ちる
- **128 トークンの自己回帰生成**: 0.5B LLM で 128 トークンの長いアクションシーケンスを正確に生成できるか。後半のトークンほど誤差が蓄積する

### 対策

- データの分布を先に可視化して範囲を決定
- ビン数は 256 / 512 / 1024 を試す

---

## 5. Flow Matching の実装難度

**Phase 6 ／ 深刻度: 中〜高**

- **CFM の正しい実装**: Flow Matching 自体が比較的新しい手法。Gaussian OT path の実装ミスが分かりにくい（loss は下がるが生成品質が悪い等）
- **150M Trajectory Decoder のアーキテクチャ設計**: 「小さな Transformer」とあるが、層数・次元・head 数の具体的な設計が未定
- **KV-cache 条件付けの実装**: Qwen2.5-0.5B から KV-cache を取り出して Trajectory Decoder に渡す部分は、transformers ライブラリの内部実装に依存

### 対策

- まず Option A（hidden states 条件付け）で動かす
- 既存の Flow Matching 実装（flow-matching ライブラリ等）を参考にする
- Trajectory Decoder は Alpamayo 10B の 2B decoder の構造比率をスケールダウン

---

## 6. RL の不安定性

**Phase 8 ／ 深刻度: 中**

- **GRPO の実装**: 標準的な PPO よりは実装が簡単だが、K=4〜8 のロールアウトでグループ内の advantage 推定が不安定になりやすい
- **報酬のバランス**: r_reason, r_consistency, r_traj の 3 つの報酬の重み付けが敏感。一つの報酬に偏ると他が崩れる
- **reward hacking**: LLM が報酬を最大化するために意味のない推論パターンを学習する可能性

### 対策

- RL は最後の Stage なので、Stage 3 の SFT モデルが十分良ければスキップも選択肢
- まず r_traj のみでシンプルに始める

---

## 7. パイプライン全体の長さ

**プロジェクト全体 ／ 深刻度: 高**

8 Phase × 各 Phase で複数のイテレーションが必要。**一つの Phase で詰まると後続が全部ブロックされる**。

```
Phase 2 (VLM) ← ここが詰まると全停止
    ↓
Phase 3-4 (Stage 0) ← ここで初めて「行動予測」が動く
    ↓
Phase 5-8 ← ここまで到達するのが遠い
```

### 対策

- Phase 2 と Phase 3 を並行で進める（VLM 完成前に Stage 0 のパイプラインだけ先に通す）
- 各 Phase の Exit 条件を厳守し、「完璧」を求めずに次へ進む
